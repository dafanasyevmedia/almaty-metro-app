## Что это

Telegram Mini App (и просто веб-страница): показывает ближайшую станцию
метро Алматы по геопозиции и обратный отсчёт до следующих поездов в обе
стороны, плюс страница полного расписания. Три языка (kk/ru/en).

**Публичная ссылка:** https://dafanasyevmedia.github.io/almaty-metro-app/
**Репозиторий:** https://github.com/dafanasyevmedia/almaty-metro-app

## Архитектура

Никакого фреймворка и сборки. Три типа файлов:

```
index.html                              — вся логика: разметка + CSS + JS в одном файле
data/stations.json                      — координаты + названия станций (ru/kk/en)
data/schedule.json                      — расписание (перегенерируется скриптом)
data/schedule_drift_log.jsonl           — диагностика: лог расхождений с прошлым запуском
                                           скрипта (см. п. 6 ниже), приложением не используется
data/icon-source.svg                    — исходник иконки (для регенерации favicon)
data/holidays.json                      — даты казахстанских праздников (обновлять раз в год вручную!)
scripts/update_schedule.py              — тянет данные с API метро, пишет два JSON выше
.github/workflows/update-schedule.yml   — запускает скрипт ежечасно (06:00–21:00 Алматы), коммитит результат
favicon*, apple-touch-icon.png,
web-app-manifest-*.png, site.webmanifest — сгенерированы на realfavicongenerator.net
                                           из data/icon-source.svg, руками не редактировать
```

`index.html` фетчит `data/stations.json` и `data/schedule.json` через
`fetch()` при загрузке — то есть локально его нужно открывать через HTTP-сервер
(`python3 -m http.server`), не через `file://` (см. README).

## Откуда данные и как работает update_schedule.py

Официальный сайт metroalmaty.kz красивый, но неудобный. Реальные данные
берутся напрямую с его бэкенда — недокументированного API
`api.metroalmaty.kz/api/v1/schedule/{slug}`, который отдаёт JSON с
расписанием на будни/выходные по двум направлениям (`direction1`/`direction2`).

Неочевидные моменты в скрипте (**обязательно прочитать перед правкой**):

### 1. API иногда отдаёт `null` вместо будних данных — временный сбой
Скрипт ретраит до 5 раз с паузой (`fetch_station_payload`). Это не связано
с конкретной станцией, случается у любой.

### 2. У конечных станций API путает direction1/direction2
Обычно `direction1` = в сторону Б. Момышулы (forward), `direction2` = в
сторону Райымбек батыра (backward). Но для станции Б. Момышулы (последняя
на линии) реальные рейсы почему-то лежат в `direction1`, хотя физически
это направление невозможно (нельзя ехать от Б. Момышулы к Б. Момышулы).
Поля `station1`/`station2` от API в этом случае тоже не помогают — они
указывают на другой сосед, чем тот, где реально лежат данные.

**Решение:** для первой и последней станции линии направление определяется
не по номеру `direction`, а по тому, где реально есть рейсы (`d1_has_data`
в `main()`). Если когда-нибудь появится третья "аномальная" станция —
этот же код её обработает автоматически, специальных случаев на неё
добавлять не нужно.

### 3. Станция Абая не отдаёт расписание на выходные вообще
Подтверждено многократно в разное время — это не сбой, а постоянное
состояние на сервере метро. Раньше (первая версия) просто копировали
будние интервалы — но это неверно: в выходные поезда ходят реже (~15 мин
против ~6 мин в будни).

**Решение (`estimate_weekend_via_neighbor`):** берём соседнюю станцию, у
которой выходные данные есть, считаем медианный сдвиг по времени в пути
между этой станцией и соседом (используя будние данные, где сверить есть
с чем), и переносим этот сдвиг на настоящее выходное расписание соседа.
Логика общая — сработает для любой станции, которая в будущем лишится
выходных данных на сервере метро, не только для Абая. Если у обоих
соседей тоже нет данных — фолбэк на старый способ (будни как оценка,
помечается флагом `weekend_estimated: true` в schedule.json).

### 4. Английских названий станций у API нет
Только ru/kk (через `current_station_locales`). Английские — статичный
словарь `EN_NAMES` в скрипте, источник — англоязычная Википедия
(https://en.wikipedia.org/wiki/Almaty_Metro), романизация оттуда
(`Zhibek Joly`, `Sayran`, `Saryarqa`, `Bauyrjan Momyshuly` — не
транслитерация с русского, а казахско-латинская, так исторически
сложилось у Википедии).

### 5. `list[str] | None` не работает на Python 3.9
На машине разработки стоит 3.9 (синтаксис `X | None` — это 3.10+).
В начале файла стоит `from __future__ import annotations` — не убирать,
иначе скрипт упадёт при запуске.

### 6. Расписание на ещё не наступившие часы дня "плывёт" у самого metroalmaty.kz
Проверено вручную (2026-08-25): расписание станции на утро/уже прошедшие часы,
снятое в разное время в течение дня, совпадает день в день до секунды. А вот
расписание на вечер (ещё не наступивший на момент снятия), снятое в 14:38 и
повторно в 20:37 того же дня, отличалось на ~2 минуты в каждой записи (тот же
интервал между поездами, но сдвинутая фаза) — то есть источник сам
пересчитывает ещё не наступившую часть дня, а не отдаёт статичную табличку на
все сутки вперёд. Два запроса подряд с разницей в 3 секунды при этом отдают
идентичный результат — не рандом на каждый запрос, а именно медленный дрейф.

**Из-за этого** `data/schedule.json` неизбежно может на несколько часов
расходиться с тем, что показывает официальный сайт прямо сейчас, для ещё не
наступившей части дня — это не баг скрипта. Смягчено частым автообновлением
(см. `.github/workflows/update-schedule.yml`, ежечасно 06:00–21:00 по Алматы) —
дальше учащать не стоит, API недокументированный, риск словить блокировку.
У API нет ни `updated_at`, ни `Last-Modified`/`ETag` в заголовках — понять,
когда именно источник обновил данные, можно только опытным путём (сравнивая
снимки), поэтому и появился `data/schedule_drift_log.jsonl`.

**`data/schedule_drift_log.jsonl`** — сравнивает новый снимок со старым перед
каждой перезаписью `schedule.json` (`diff_schedules()`/`log_drift()` в
update_schedule.py). Одна JSON-строка за запуск: `changed_count` + список
`changes` (какая станция/день недели/направление, сколько записей было/стало,
первое расхождение). `changed_count: 0` — тоже важная запись, подтверждает, что
джоба реально проверяла и просто ничего не изменилось (иначе непонятно, пропуск
в логе — "не менялось" или "джоба не запустилась"). Не используется
приложением, чисто диагностика — если через какое-то время станет ясно, как
часто на самом деле дрейфуют данные, можно удалить этот файл и код вокруг него.

## Ключевые неочевидные решения в index.html

### Границы "транспортных суток" (после полуночи)
Метро работает ~06:20–00:15/00:30. Время после полуночи (`hour < 3`)
считается хвостом *текущих*, а не следующих суток — так и в сырых данных
API (последние записи дня — вида `"00:16:00"`), и в логике приложения
(`timeStrToMinutes`, `serviceDayStart`). Это влияет на:
- Какой день недели (будни/выходные) действует прямо сейчас
- Сортировку в таблице полного расписания (00:xx должно идти в конце,
  а не в начале — уже была ошибка на этом, см. историю коммитов)
- Расчёт "первого поезда завтра" при показе "метро закрыто"

Если трогаете `buildTimeline`/`nextTrains`/`serviceDayStart` — сначала
проверьте вручную на границе полночь/будни-выходные, там уже дважды
находились баги.

### Заглушка Telegram вне настоящего Telegram-клиента
`telegram-web-app.js`, загруженный не внутри Telegram (обычный браузер,
тестирование), не выкидывает ошибку — а подставляет молчаливую заглушку:
`platform === 'unknown'`, `colorScheme` всегда `'light'`, `LocationManager`
может никогда не вызвать колбэк. Проверка `insideTelegram` (по `platform`)
и таймаут-фолбэк на геолокации — обходят это. **Не убирайте эти проверки** —
без них тёмная тема и геолокация в обычном браузере молча ломаются.

### i18n (три языка)
Словарь `I18N.{ru,kk,en}` — плоский объект строка→строка или
строка→функция (для строк с подстановкой значений). `t('key', ...args)` —
достаёт перевод, вызывает как функцию если нужно. `stationName(station)` —
аналог для названий станций (объект `{ru,kk,en}` в data/stations.json).
`applyLanguage(lang)` перерисовывает весь текущий экран и запоминает
выбор в `localStorage`. Если добавляете новый текст в интерфейс — не
хардкодьте строку в JS/HTML, добавляйте ключ во все три языка сразу.

### Не полагаться на `toLocaleDateString` для казахского
Некоторые WebView (в т.ч. часть окружений внутри Telegram) не имеют
полных данных локали `kk` и откатываются к ISO-формату даты
(`2026-08-01`) вместо человеческого. Дата в футере форматируется вручную
(`fmtDate`) — не заменять обратно на `toLocaleDateString`.

### "Не в Алматы" — порог 30 км
`FAR_FROM_ALMATY_METERS = 30000`. Выбран с запасом на город + ближние
пригороды (Медеу и т.п.), но чтобы отсекать соседние города вроде Есика.

### Праздничные дни (`data/holidays.json`)
Официального API с праздниками нет — список дат хранится вручную в
`data/holidays.json` (плоский массив `"YYYY-MM-DD"` в поле `dates`).
`dayTypeOf()` в `index.html` проверяет и день недели, и попадание даты в
этот список — если попал, весь день (включая расчёт "первый поезд завтра"
на закрытии) считается выходным, без изменений в остальной логике.

Список включает **два вида дат**, вперемешку (для кода разницы нет):
1. Сами календарные даты праздников.
2. Официально перенесённые выходные дни — когда праздник выпал на субботу
   или воскресенье, государство переносит выходной на другой день, и это
   **не формула "плюс один день"**: правительство публикует конкретную
   дату переноса каждый год отдельным постановлением. Например, в 2026
   году Наурыз (сб 21 и вс 22 марта) перенесён не на понедельник 23-е (он
   и так уже праздник, третий день Наурыза), а на вторник-среду 24-25
   марта. Считать самостоятельно нельзя — нужно смотреть опубликованный
   список.
   **Исключение:** Рождество (7 января) и первый день Курбан-айта **не
   переносятся**, даже если выпадают на выходной.

**Требует ручного обновления раз в год.** Два источника проблем:
- Курбан-айт определяется по лунному календарю (хиджре) и сдвигается на
  ~10-11 дней каждый год — дату нельзя посчитать заранее, только смотреть
  публикации ближе к дате.
- Переносы выходных на конкретный год публикуются правительством обычно
  не сильно заранее (для 2027 года на момент написания этого файла ещё не
  опубликованы — см. `_note_2027` в `data/holidays.json`).

#### Календарь работает в обе стороны (`workingWeekends`)

По ст. 85 ТК РК власти могут не только сделать будний день выходным, но
и наоборот — объявить субботу (реже воскресенье) рабочим днём, чтобы
"одолжить" её выходной статус и слепить длинный блок выходных вокруг
праздника. Пример: праздник во вторник → суббота перед ним объявляется
рабочей → её выходной день "переезжает" на понедельник → в сумме три
дня подряд выходных (вс-пн-вт) при одной рабочей субботе.

`data/holidays.json` поэтому содержит два массива:
- `dates` — будни, ставшие выходными (описано выше).
- `workingWeekends` — выходные, ставшие буднями (обратный случай).

`dayTypeOf()` проверяет `workingWeekends` **первым** (приоритет над
обычной проверкой дня недели): если дата там — `weekday`, независимо от
того, что это суббота/воскресенье. Помогающие функции:
`isWorkingWeekendDate()`, `isWeekendForcedWorkday()` (последняя — для
показа пояснения в интерфейсе, см. `workdayNote`/`fullWorkdayNote`,
зеркальны `holidayNote`/`fullHolidayNote`).

На 2026-2027 годы подтверждённых случаев такого переноса не найдено —
Казахстан пока использует только продление (см. выше), поэтому
`workingWeekends` пуст. Но механизм законный (проверено) и реализован
заранее — при ежегодном обновлении списка праздников стоит заодно
проверять, не появился ли такой перенос.

Источники дат на 2026 год: [egov.kz](https://egov.kz/cms/ru/articles/employment_relations/holidays-calend)
(сами праздники) и [informburo.kz](https://informburo.kz/novosti/perenosy-vyxodnyx-i-kurban-ait-v-mae-kalendar-prazdnicnyx-dnei-v-kazaxstane-na-2026-god)
(переносы). Проверять оба раза в год ближе к декабрю/январю.

### Цветовая палитра
CSS custom properties в `:root` — единственное место, где менять цвета.
Тема "Metro" (синяя) выбрана пользователем из двух вариантов после
превью-версии (см. историю чата/коммитов, если нужен контекст выбора).
Есть три слоя переопределения: `prefers-color-scheme: dark` (системная
тёмная тема), `[data-tg-theme]` (тема самого Telegram, только внутри
настоящего клиента). Если меняете палитру — трогайте только значения
переменных, не структуру селекторов.

### Google Analytics (GA4)
Стандартный сниппет `gtag.js` в `<head>` `index.html`, Measurement ID
`G-Q7NT3NLEJY`. Меняется/удаляется — просто заменить/убрать эти два `<script>`
тега, больше нигде ID не используется. У части посетителей события не долетят —
блокировщики рекламы в браузере (uBlock и т.п.) режут `googletagmanager.com`;
внутри самого Telegram (WebView) блокировщиков нет, там считается исправно.

Кроме автоматических событий самого GA (просмотр, скролл и т.п.) отправляются
свои — через `trackEvent(name, params)` (обёртка над `gtag('event', ...)`,
защищена try/catch на случай, если блокировщик вырезал сам `gtag`, чтобы
аналитика не роняла приложение):

- **`select_station`** — `{station, method}`, method: `geo` (по геолокации),
  `manual` (сам выбрал — список или точка на линии), `default` (авто-фолбэк на
  первую станцию, когда геолокация недоступна/далеко — не осознанный выбор).
- **`switch_tab`** — `{tab}`: `nearest` / `full` / `about`.
- **`geo_result`** — `{result}`: `ok` / `far` / `denied` / `unsupported` / `error`.
- **`change_language`** — `{lang}`, только при ручном клике по кнопке языка (не
  при автоопределении на старте — иначе событие искажало бы картину).
- **`schedule_load_error`** — `{message}`, если не загрузились данные
  (`data/stations.json`/`schedule.json`/`holidays.json`) — сигнал о реальной
  поломке, а не про использование.

Никаких координат/личных данных в параметрах — только слаги станций и коды
результатов.

## Как продолжить работу

1. Открыть эту папку в Claude Code (или другом ассистенте) — этот файл
   подхватится автоматически как контекст проекта.
2. Локальный тест: `python3 -m http.server 8765` из этой папки, открыть
   `http://localhost:8765`.
3. Изменения в `index.html` видны сразу после перезагрузки страницы.
4. Изменения в данных — через `python3 scripts/update_schedule.py`
   (перезапросит API метро заново).
5. Публикация — обычный git push, GitHub Pages пересоберётся сам за
   1-2 минуты (Source: Deploy from branch, уже настроено).

## Известные ограничения (не баги, а факты о данных)

- Расписание статическое (как на официальном сайте) — не GPS-трекинг
  поездов в реальном времени, а расчёт по таблице интервалов.
- Праздничные дни не учитываются — API их не размечает отдельно.
- Английские названия станций не от официального источника метро (его
  нет), а с Википедии — при желании можно заменить на другие романизации
  в `EN_NAMES` (scripts/update_schedule.py).
